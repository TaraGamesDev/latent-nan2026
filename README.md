# LATENT

**덮인 나사에는 아직 색이 없습니다.**

철판이 여러 겹으로 볼트 고정된 벽을 나사를 하나씩 풀어 해체하는 퍼즐.
푼 나사는 홀더 3칸 중 하나로 들어가고, 홀더는 처음 들어온 색으로 잠긴 뒤
같은 색 3개가 모이면 비워집니다. 여기까지는 익숙한 형태입니다.

다른 점은 하나뿐입니다 — **레벨이 미리 존재하지 않습니다.**
판에 덮인 나사에는 색이 없습니다. 숨겨진 게 아니라 **아직 결정되지 않은** 것이고,
위의 판이 떨어져 손이 닿는 순간 AI가 **당신의 그 시점 상황을 보고** 색을 정합니다.

## 왜 이게 중요한가

캐주얼 퍼즐의 원가는 **레벨 뱅크**입니다. 수천 개의 레벨을 사람이 만들고,
그보다 더 비싼 일 — **만든 레벨이 풀리는지 검증** — 을 합니다.

레벨을 미리 만들지 않으면 **그 검증 단계가 통째로 사라집니다.**

```
나사에 손이 닿을 때마다
   │
   ├─▶ [스킬 추정기]  src/ai/skill.ts
   │     regret = value(솔버의 최선수) − value(플레이어가 고른 수)
   │     → θ(숙련도), {계획성 · 정돈 · 템포}, {좌절도 · 지루함}
   │
   ├─▶ [배정기]       src/ai/assigner.ts        ← 의도
   │     θ + 감정 + 벽 진행 램프 → 목표 난이도
   │     구제 확률 = (홀더 위험도 × w + 기본값) × (1 − 실력가중 × 목표)
   │
   ├─▶ [완결성 검사]  같은 파일                   ← 시공
   │     ★ 색 미결정 나사 수 ≥ 3의 배수를 맞추는 데 필요한 나사 수
   │     ★ 지금 둘 수 있는 수가 하나도 없어지는 색은 쓰지 않는다
   │
   └─▶ [글래스박스 패널] src/ui/panel.ts
         위 전부를 화면에 그대로 노출
```

**런타임은 전부 결정론적입니다.** 네트워크도, API 키도, 계정도 필요 없습니다.

## 핵심 설계 세 가지

### 1. 수순당 후회(regret)로 실력을 잰다

"레벨을 클리어했는가"는 몇 분에 한 번 오고, 그 레벨이 마침 쉬웠는지에 오염됩니다.
대신 **모든 탭을, 그 탭이 이루어진 바로 그 국면에서** 솔버의 최선수와 비교합니다.
국면이 통제되어 있으므로 "쉬워서 잘한 것"과 "실제로 잘 둔 것"이 섞이지 않습니다.

### 2. 의도와 시공을 분리한다

배정기는 *"지금 이 순간이 어떻게 느껴져야 하는가"*만 정합니다.
실제로 색을 쓰기 전에 **완결성 부등식**이 별도로 검사합니다.
플레이어를 평가하는 쪽은 틀려도 되지만, **나사에 색을 쓰는 쪽은 틀리면 안 되기 때문**입니다.

### 3. 약속은 작게, 대신 반드시 지킨다

> **이 벽은 끝까지 해체 가능합니다.** 그리고 색을 쓰는 순간에는 **둘 수 있는 수가 최소 하나** 있습니다.

이보다 강한 약속은 하지 않습니다. "해체 가능한 벽"과 "이 플레이어가 해체할 벽"은
다른 말이고, 후자를 약속하는 순간 게임이 사라집니다. 홀더가 3칸이므로 살아 있는 색이
4종만 되어도 갈 곳 없는 색이 생기고, 3종으로 묶으면 **런이 아예 끝나지 않습니다** —
실제로 그렇게 만들었더니 세 페르소나가 전부 3,000탭 상한까지 살아남았습니다.

## 직접 확인해 보기

**AI 패널** (우상단 버튼 또는 `D` 키):

- 지금 시스템이 당신을 어떻게 추정하는지 (θ와 세 하위 지표, 좌절도/지루함)
- 숙련도 · 목표 난이도 · 실제 난이도가 겹쳐 그려지는 **플로우 채널**
- **방금 정한 색의 근거** (한국어 문장)
- **검토된 후보 색들과 채택되지 않은 것들**, 완결성 판정 포함
- 불변식 검증: 색 미결정 나사 ≥ 필요 나사
- 패널이 열려 있으면 **AI가 방금 결정한 나사가 화면에서 강조**됩니다

## 개발

```bash
npm install
npm run dev     # localhost:5173
npm run build   # docs/ 로 빌드 (GitHub Pages)
npm run bench   # 헤드리스 엔진 검증 (페르소나당 300런)
npm run margin  # 이 규칙에서 실력이 얼마나 값어치가 있는지 측정
```

`npm run bench`는 봇 페르소나로 전체 게임을 **실제 `tap()` 경로**로 돌리고
네 가지를 **단언**합니다: 완결성 불변식 유지 / 약한 플레이어는 반드시 패배 /
실력이 실제로 값을 함 / θ가 페르소나를 마땅한 순서로 정렬.

## 실력 마진은 예산이다

`npm run margin`은 배정기를 얼려 놓고 **규칙 자체에서 실력이 얼마나 값어치가 있는지**만 잽니다.

```
최선수만 두기   9.67 벽      실력 마진 (최선수/무작위)     7%
무작위 합법수   9.04 벽      순위 스프레드 (최선수/최악수) 2.29배
최악수만 두기   4.22 벽      한 턴에 닿는 나사 4.3개
```

이 7%가 **적응의 예산**입니다. 숙련자의 난이도를 실력 마진보다 더 올리는 적응은,
원리가 아무리 옳아도 순위를 뒤집습니다 — 실제로 첫 튜닝에서 초보가 숙련자보다
멀리 갔고(n=300에서 7.87 vs 6.97), 원인은 게이트가 θ의 **임계값**으로 풀리도록
되어 있어 실력이 절벽으로 도착한 것이었습니다.

같은 도구가 더 근본적인 버그도 잡았습니다: 국면 평가가 *"이 홀더를 끝낼 수 있는가"*를
묻지 않아 **솔버의 최선수를 따를수록 성적이 나빴습니다.** 그 상태에서 계산한 regret은
전부 무의미했습니다.

## 이 규칙을 고른 근거

세 가지 후보를 **같은 축(정확한 검증 비용)** 으로 재고 골랐습니다. `src/probe/`:

| 후보 | 검증 처리량 | 정확성 |
|---|---|---|
| A · STAMP (GF(2) 토글) | 85,228 레벨/초 | 완전 정확 (풀림·최소수·해 개수) |
| B · MAGNET (당기기) | 26 레벨/초 | 불완전 — 깊이 제한, 미해결은 *미지* |
| **C · 지연 결정** | **470,000 결정/초** | 검증 단계 자체가 없음 |

B가 A보다 3,300배 느린 이유가 이 프로젝트의 논지입니다. 소코반이
PSPACE-complete라서 레벨 자동 생성이 *논문 주제*인 것과 같은 이유입니다 —
**비싼 건 생성이 아니라 검증입니다.**
